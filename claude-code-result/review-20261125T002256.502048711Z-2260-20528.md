# Independent review — computer-management (fleet)

Scope: the working tree is clean (`git status` shows no staged, unstaged or untracked changes outside ignored dirs), so this is a review of the code at `HEAD` (`b5bd315`). I read the security-critical files you listed, all 7 modules, both workflows plus the release workflow, the Makefile, all three test tiers' entry points, and the English docs (`docs/design.md`, `docs/platforms.md`, the release/TLS parts of `README.md`, `docs/provisioning.md`). I also checked recent GitHub Actions run history with `gh run list`.

I did not run any code or tests. Platform-behaviour claims are from my own knowledge of the OS. Each one is labelled with how confident I am.

Items you listed as known and deliberate (drift only re-checked on a generation change, no session tier, no self-update, macOS tier 3 never run, `browser.default` nudge-only) are not reported as findings. They are mentioned only where a separate bug sits on top of them.

## Critical / High

### H1. A compromised server, or anyone holding the signing key, can run arbitrary code as root/SYSTEM. This contradicts the design's central security claim.
- `internal/agent/modules/file.go:33-102`: `file` accepts any absolute path, any content and any mode, writes as root/SYSTEM, and the server never validates `config` (`internal/policy/policy.go:82-112` only checks id/type/class). Examples: `/etc/cron.d/x`, `/Library/LaunchDaemons/x.plist`, `/etc/sudoers.d/x`, `C:\Windows\System32\...`, or overwriting `/usr/local/bin/fleet-agent` / `C:\Program Files\Fleet\fleet-agent.exe` itself. Any of these is code execution at the next boot or poll.
- `internal/agent/modules/packages.go:89-111`: package names go straight into argv with no check for a leading `-`. A `packages` item with `"name": "-oDPkg::Pre-Invoke::=/bin/sh -c '…'"` next to any real package becomes `apt-get install -y -oDPkg::Pre-Invoke::=…`, which is a documented apt hook that runs a shell command. `dpkg-query` fails on that "name", so it is classed as missing and always passed to the install command. `winget`/`brew` have similar flag injection.
- `internal/server/server.go:68-95`: the signing seed sits on disk next to the DB on the same host, so a server compromise gives up the key too. The signature protects only against a network MITM, not against a compromised server.
- The docs say the opposite: `docs/design.md:44-45` ("The server holds no long-lived credential that grants arbitrary code execution on a device") and `docs/design.md:294-297` ("the agent has no `exec` primitive reachable from the wire … single most important property"). The same claims are in `design.zh-CN.md`.
- **Fix direction:**
  - Restrict `file` to an allow-list of path prefixes compiled into the agent, and reject autostart, sudoers and the agent's own paths.
  - Reject package names and ids starting with `-`, and put `--` before positional arguments where the manager supports it.
  - Validate module config on both sides.
  - Or correct the docs to say a compromised server equals root on every device.
- This is a defect against the stated design, not a judgement call.

### H2. On Windows, a standard user can take over `agent.json`, which gives local privilege escalation to SYSTEM and lets them fake compliance.
- `internal/agent/config.go:51-64`: `Save` uses `os.MkdirAll(..., 0o700)` and `os.WriteFile(tmp, ..., 0o600)`. On Windows those mode bits are ignored, and `C:\ProgramData\fleet` (`config.go:30`) inherits the default ProgramData ACL: `BUILTIN\Users:(OI)(CI)(RX)` and `BUILTIN\Users:(CI)(WD,AD,WEA,WA)` (create files), plus `CREATOR OWNER:(F)`. As a result:
  1. Any local user can **read** `device_secret`. With it they can call `/api/v1/report` and post "compliant" for every item. `handleReport` (`server.go:264-288`) accepts any reports for that device. `docs/design.md:304-305` says the secret "is only useful to fetch that device's own policy", which is wrong.
  2. The temp file name is fixed (`path + ".tmp"`). A standard user can pre-create `C:\ProgramData\fleet\agent.json.tmp`, and the user owns it. `os.WriteFile` as SYSTEM truncates and writes into it, then `os.Rename` moves it over `agent.json` with the user's ACL intact. The user now owns the config and can change `server_url` + `signing_key` (their own "server"), `root`, or `dry_run`. Combined with H1, that is SYSTEM code execution. `dry_run: true` also makes every module report `drifted`/"would …" while doing nothing.
- `scripts/install-windows.ps1` sets no ACL on `ProgramData\fleet`, and `test/e2e/guest/verify.ps1` doesn't check one.
- **Fix:**
  - Create the directory with an explicit protected DACL (SYSTEM + Administrators only, inheritance disabled).
  - Use `os.CreateTemp` (random name) for the config temp file.
  - Add a `verify.ps1` assertion that `icacls` on the directory and the file shows no `Users`/`Authenticated Users` access.
- Confidence: high on the default ProgramData ACL and on rename keeping the source file's security descriptor.

### H3. `user.account` reports "standard user / compliant" for some real administrators.
`internal/agent/modules/user_account.go:141-150` `containsUserLine` splits on `-` (and `:`), and compares case-sensitively.
- A user named `jean-luc` is never matched. They show as non-admin, the report is `compliant` and demote is never attempted.
- On Windows, `net localgroup Administrators` lists names in their stored case and, for domain/AAD members, as `DOMAIN\alice` / `AzureAD\alice`. Policy `"username": "alice"` therefore doesn't match `Alice` or `AzureAD\alice`, and the result is `compliant` while the user is an admin.
- Nested membership (a group inside Administrators, or nested groups in macOS `admin`) is also not seen.

This is exactly the "agent claims compliance when the effect is absent" case, on the control `docs/design.md:71-74` calls "the single highest-leverage control in the whole design". Also, `user_account.go:78`: if the post-demote check *errors*, the code falls through to `StatusChanged` ("now a standard user") without having verified it.
- **Fix:**
  - Windows: use `Get-LocalGroupMember`, or compare SIDs (case-insensitive and domain-aware).
  - macOS: use `dseditgroup -o checkmember -m <user> admin`, which handles nested groups.
  - Linux: `id -nG` as today.
  - Treat a verification error after demote as `error`.
- Tests: neither `verify.sh` nor `verify.ps1` uses a username with `-` or a case mismatch.

### H4. `macos.consent` reports App Management as granted on a Mac that has Firefox but has never been given the grant.
- `internal/agent/modules/firefox.go:175-182` and `module.go:170-173`: `fileExists` returns false for directories, and `/Applications/Firefox.app` is a directory. So `HasFirefox` is **always false on macOS**, and `inventory` always reports `firefox: false`.
- `internal/agent/modules/consent.go:87-90` relies on the same check: `!fileExists(policies.json) && !fileExists(Firefox.app)` is true whenever `policies.json` doesn't exist yet. The probe then returns `true` ("no Firefox, nothing to grant") without trying the write.
- On a fresh machine, which is exactly when consent matters, the result is `consent: compliant / granted.app_management=true` even though App Management was never granted.
- Bundle items are sorted by ID on the server (`server.go:310`), so `consent` runs before `firefox`. In the same report, `consent` says granted and `firefox` then says `action_required: App Management consent is required`.
- When the probe does run, it also calls `os.MkdirAll` on `…/Firefox.app/Contents/Resources/distribution` (`consent.go:92`). That mutates a signed bundle from a module documented as detection-only.
- Why tier 2 misses it: `verify.sh:193` only checks `compliant ⇒ policies.json exists`. On the runner the Firefox write that follows succeeds, so the false `compliant` passes.
- **Fix:**
  - Use `os.Stat(...).IsDir()` for `.app` probes.
  - Report `not_applicable`/`unknown`, not "granted", when the app is missing.
  - Don't create directories in the probe.

## Medium

### M1. A failed report is never retried, and the server can't tell stale reports from current ones.
- `internal/agent/agent.go:127-137`: if `Report` fails, the agent still persists the new `Generation`. The next `Once` returns at `agent.go:121-124` ("policy unchanged") *before* applying or reporting. The comment "the next cycle will report again" is false: the reports for that generation are lost until the policy changes.
- Server side, `handleReport` (`server.go:264-288`) ignores `req.Generation`, and `SetDeviceReports` stores no generation. A late or replayed report for an older generation overwrites newer state. The dashboard (`handleListDevices`) cannot show whether the compliance counts relate to the current policy.
- **Fix:**
  - Agent: persist the generation only after a successful report, or keep the last reports and resend them while unacknowledged.
  - Server: store `reported_generation` and reject reports whose generation is not the device's current one.

### M2. Plain HTTP is accepted at enrolment, where the signing key is pinned.
- `internal/agent/agent.go:59-82` and `client.go:23-30`: any `-server` URL scheme is accepted, and the signing key is taken from the enrolment response over that transport. On `http://`, a network MITM at enrolment time pins their own key, then (via H1) owns the device permanently. The device secret also travels in clear.
- `docs/design.md:247-248` says TLS is "the deployment's responsibility". Judgement call, but cheap fix: refuse non-`https` URLs except loopback or an explicit `-insecure` flag, and/or let the operator pass `-signing-key <b64>` at enrol time to avoid TOFU.

### M3. `browser.default` detection on macOS can never return a real answer, and on every OS it reads the wrong user.
- `browser_default.go:114-129` searches for `lsHandlerURLScheme = https` (lower-case `l`) and then looks *forward* to the next `}`. Real `defaults read` output, to my knowledge (fairly confident, please check on a real Mac), uses `LSHandlerURLScheme`. Keys are printed alphabetically, so `LSHandlerRoleAll` comes *before* `LSHandlerURLScheme`. There is also a nested `LSHandlerPreferredVersions = { LSHandlerRoleAll = "-"; };` whose `}` ends the scan early. The result is always `unknown`, so always `action_required`, even when Firefox is default. The unit-test fixtures (`browser_default_test.go:18-36`) use the same invented shape, so the tests can't catch it. The doc repeats it (`docs/platforms.md:247`).
- The daemon reads *its own* user: `defaults read` as root reads `/var/root/...`, `reg query HKCU` as SYSTEM reads the S-1-5-18 hive, and `xdg-settings` as root reads root's config. Not having a session tier is a known limitation, but here the module *reports* root's or SYSTEM's state as `observed`. If root happens to match, it reports `compliant` for a state that has nothing to do with the user. Prefer returning `action_required` with "cannot observe from the executor tier" until the session tier exists.
- Tier 2 masks it: `verify.ps1` runs `once` as the elevated runner user, not SYSTEM. On both platforms the "gives the user an action" check accepts `action_required|compliant`, so a detector that always says `unknown` passes.

### M4. `firefox.policy` writes a policy for a Firefox that isn't installed and reports `changed`. One rendered policy key doesn't exist in Firefox.
- `firefox.go:56-81` never checks the install. On macOS without Firefox it creates `/Applications/Firefox.app/Contents/Resources/distribution/` (a fake app directory). On Windows it writes `C:\Program Files\Mozilla Firefox\distribution\policies.json` even if Firefox is in `Program Files (x86)`, per-user, or absent. Either way it reports `changed` for an effect that doesn't exist.
- `firefox.go:151-153` emits `DefaultBrowserSettingEnabled`. To my knowledge that is a Chromium/Edge policy. Firefox's equivalent is `DontCheckDefaultBrowser`, and Firefox ignores unknown policy names (shown as an error in `about:policies`). So `default_browser_check` does nothing while the item reports compliant. `docs/platforms.md:117` documents the wrong key. `platforms.md:118` also lists `DisableFirefoxAccounts`, which the code never emits.
- The permission-error branch (`firefox.go:70-78`) always says "App Management consent is required … System Settings", even on Windows/Linux. The status is right but the message misleads.

### M5. `packages` cannot work as deployed on macOS or Windows, and winget installs only the first missing package.
- `packages.go:111-115`: for winget, `installArgs` returns only `pkgs[0]`. The comment says "the caller loops below", but no caller loops. With two missing packages, one is installed, the re-check reports `error`, and (no timer) the second is never retried until the policy changes.
- macOS: the LaunchDaemon PATH has no `/opt/homebrew/bin`, so the result is `unsupported`. Even with brew found, Homebrew refuses to run as root. `hasPackage` swallows that error (`packages.go:149-153`) and treats every package as missing. `docs/design.md:306` claims "the executor drops to a dedicated user for package-manager work", which isn't implemented.
- Windows: `winget` is an App Execution Alias that is not on SYSTEM's PATH. `LookPath("winget")` fails under the service, so the result is `unsupported`. `docs/platforms.md:126-127` says the agent "runs it as SYSTEM with `--scope machine`". The code passes no `--scope`.
- The brew presence check matches substrings: `strings.Contains(out, ref+" ")` makes `git` match `libgit 1.0`, and `HasSuffix` makes `fox` match `firefox`. That gives false `compliant`. Parse per line and compare the first field.
- None of this is reachable in tier 2, because neither `verify.sh` nor `verify.ps1` includes a `packages` item.

### M6. `[release]` pushes cancel the normal CI runs, and the release gate can itself be cancelled.
- `ci.yml:10-12` and `os-e2e.yml:22-24` use `concurrency: group: ci-${{ github.ref }}` / `os-e2e-${{ github.ref }}` with `cancel-in-progress: true`. When `release.yml` calls them via `workflow_call`, `github.ref` is the same `refs/heads/main`, so the gate and the push-triggered runs share a group and cancel each other.
- Run history shows it: for `b5bd315 … [release]`, the push-triggered `ci` (45515405856) and `os-e2e` (45515405876) were **cancelled**. For `756060f` (release run 45513317031), `ci`/`os-e2e` were cancelled and the release **failed**.
- Not a bypass (cancelled ⇒ `build` skipped), but every `[release]` commit leaves red/cancelled CI on `main`. The release itself depends on which run starts first, and any push to `main` during a release cancels its gate.
- **Fix:** in the called workflows, key the group on `github.workflow`/`github.run_id` when `github.event_name == 'workflow_call'` won't work (that context reports the caller's event), so instead pass an input such as `concurrency_suffix`. Or drop `concurrency` from the reusable workflows and put it in a thin wrapper.

### M7. Manual and tag releases can be cut from unreviewed commits.
- `release.yml:110-120`: on a tag push and on `workflow_dispatch`, `prepare` never checks that `github.sha` is reachable from `origin/main`. Anyone with write access can choose any branch in "Run workflow", or push a `v*` tag on any commit, including an unmerged branch.
- The gate runs the tests on that commit, but nothing requires review, and the result is published as the latest release (not a prerelease unless chosen).
- Branch protection on `main` and tag-protection rulesets cannot be seen from the repo, so this is partly a judgement call. Add `git merge-base --is-ancestor "$GITHUB_SHA" origin/main || exit 1` in `prepare` (unless `prerelease`), and a tag ruleset restricting `v*` creation.

### M8. Workflow token permissions are wider than needed.
- `release.yml:46-47` sets `permissions: contents: write` at workflow level. That token is inherited by `prepare`, `build`, and the reusable `ci.yml`/`os-e2e.yml`.
- Those workflows run the whole test suite with `sudo` on macOS and elevated on Windows, plus third-party actions pinned by moving tag (`actions/*@v4`, `softprops/action-gh-release@v2`), all with a repo-write token.
- **Fix:**
  - Set `permissions: contents: read` at the top.
  - Keep `contents: write` only on `publish`.
  - Pin `softprops/action-gh-release` to a commit SHA, since it receives the write token.
- `ci.yml`/`os-e2e.yml` themselves declare no `permissions:` and so take the repo default. Set `contents: read` there too.

## Low

- **L1** `release.yml:83-101`: `next_version` strips the pre-release suffix and then bumps it, so after `v0.3.0-rc1` the next auto version is `v0.3.1`, skipping `v0.3.0`. Also, `git describe` only sees tags reachable from HEAD. A tag cut from a branch (M7) is invisible to `main`, so the next auto-bump can collide ("tag already exists").
- **L2** `file.go:64-71`: modes like `"4755"` parse, but `os.FileMode(0o4755)` doesn't map to `ModeSetuid`. The setuid bit is silently dropped, `Perm()` matches, and the item is reported `compliant`. Reject modes above `0o777` or map the special bits explicitly. Relative paths are accepted and resolve against the daemon's working directory (`/` or `System32`); require absolute paths. `owner` is documented in `design.md:203` but not implemented.
- **L3** `server.go:68-95`: if the key file is missing (for example a misconfigured volume), the server silently generates a **new** key. Every enrolled agent then rejects every bundle with `ErrBadSignature`, and the backoff in `agent.go:189` hides it. Refuse to start with an existing non-empty DB and no key, unless `-init-key` is passed.
- **L4** `server.go:383`: the audit entry for `device.policy` records only the group, not the override payload. `group.policy` records only the item count. `design.md:264-265` promises `payload` in an append-only log. `Audit` errors are discarded.
- **L5** `policy.go:41-56`: `ReportOnly` falls into the `default` branch and maps to `TierSession`. That makes `report_only` legal only for `inventory`. `user.account`, `firefox.policy` and the others can't be declared report-only, despite `design.md:303` ("`report_only` is the default class for anything new"). The agent also doesn't enforce class semantics: a `report_only` item goes to the same `Apply`.
- **L6** `browser_default.go` `normalizeBrowser`: `chromium.desktop` and `org.chromium.Chromium` map to `unknown`, because "chromium" doesn't contain "chrome". Minor.

## (d) Test gaps where a bug passes all three tiers

1. **The idempotency checks don't test idempotency** (`verify.sh:203-211`, `verify.ps1:208-217`, `scripts/e2e.sh:90-92`). The second `once` gets the same generation and returns at `agent.go:121-124` *before any module runs*. "Policy file not rewritten" and "generation unchanged" are therefore true even for a module that rewrites every time or reports `changed` forever. To actually exercise it, bump the generation with an unrelated item change and assert the firefox item is `compliant` (not `changed`) with an unchanged mtime.
2. **The consent check can't fail on `action_required`.** `verify.sh:192`: `[ ! -f "$POLICY" ] || true; pass …` always passes. The `compliant` branch misses H4, because the following Firefox write succeeds on the runner.
3. **The browser checks pass for a detector that always says `unknown`.** Both suites accept `action_required|compliant` (`verify.sh:200`, `verify.ps1:206`), and unit fixtures mirror the code's own assumption about `defaults` output (`browser_default_test.go:18-36`). M3 goes undetected. Assert `detail.observed` is not `unknown` when the runner has a known default.
4. **`verify.ps1` runs the agent as the elevated runner user, not as SYSTEM** (`verify.ps1:167`). Wrong-hive reads (M3), missing winget on SYSTEM's PATH (M5) and the `ProgramData` ACL (H2) are invisible. A step that runs `once` as SYSTEM (`PsExec -s`, or a one-shot scheduled task as SYSTEM) would catch all three. On macOS, `verify.sh` runs `once` via `sudo` from a GUI-capable runner session, not as a LaunchDaemon, so launchd's minimal PATH (M5) isn't exercised.
5. **No `packages` or `file` items in any tier-2 suite.** That is the module with the most platform behaviour (M5) and the one with the biggest security surface (H1). `AGENTS.md` asks for an assertion in `verify.*` for platform-facing modules.
6. **No user.account edge cases.** No hyphenated usernames, case mismatch, or domain/AAD-style members (H3).
7. **No test that a failed report is retried, or that the server rejects reports for a stale generation** (M1).
8. **No negative test for argument injection or path restrictions in `file`/`packages`** (H1).
9. **`scripts/e2e.sh:102`**: `compliant + action_required >= 2` accepts almost any outcome. Assert per-item status instead.
10. **The "code identity" section** (`verify.sh:235-277`) checks `codesign`'s behaviour, not the agent's. That is fine as documentation of the mechanism, but it isn't regression coverage. No assertion checks that `install-unix.sh` keeps a stable identity across reinstalls, which is what TCC grants depend on.
11. **Unchecked placeholder in `verify.ps1`.** Line 161 `Check "group policy accepted" $true` always passes. If the API call fails, the script throws instead, and since it then exits without writing `C:\fleet-e2e-results.json`, the uploaded artefact is empty.

## Additional judgement calls (not defects)

- On Intel Macs Homebrew `chown`s `/usr/local/bin` to the installing user, and `install-unix.sh:36-37` and the launchd plist put the root daemon's binary there. If that user is later demoted to standard, as the design requires, they still own the directory. They can then replace `/usr/local/bin/fleet-agent`, which gives root on the next launch. Consider `/usr/local/libexec/fleet/` or `/Library/Fleet/`, root-owned, and check ownership in the installer.
- Bundles have no expiry or freshness check (`IssuedAt` is ignored). A MITM can't forge policy, but it can freeze a device on an old policy indefinitely. That would show only as `last_seen_at` staying current while the generation doesn't move.
- Removing an item from policy doesn't revert its effect (for example `file`, or the Firefox policy file). That is reasonable, but it is undocumented.
